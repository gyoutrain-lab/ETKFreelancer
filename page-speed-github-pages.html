Page Speed & Core Web Vitals for GitHub Pages

A GitHub Pages website can be extremely fast, but many projects become slower over time because of large images, unnecessary scripts, blocking resources, and unoptimized page structure. Performance is not only a user experience issue; it also affects crawling efficiency, engagement, and long-term SEO quality.

This guide explains the same performance principles used on the ETKFreelancer project, with a focus on Core Web Vitals, render-path optimization, and practical improvements that do not require a complex build system.

Why Page Speed Matters for SEO

Google uses page experience signals as part of its broader quality evaluation. A fast page is easier to crawl, easier to render, and more likely to keep visitors engaged. For small business websites and GitHub Pages projects, performance improvements often create benefits that go beyond loading time.

SEO-related benefits of a faster site:
  • Lower bounce rates
  • Better mobile experience
  • Faster rendering for Googlebot
  • Improved engagement metrics
  • Better conversion potential

A page that loads quickly helps users reach the content with less friction. Search engines can also process lightweight pages more efficiently, which is especially useful when a website contains multiple articles, portfolio pages, or technical guides.

Performance should therefore be treated as part of technical SEO, not as a separate optimization task. On GitHub Pages, many of the largest gains usually come from image optimization, reducing unnecessary scripts, and keeping the page structure clean and easy to render.

Understand the Three Core Web Vitals

Largest Contentful Paint (LCP)

Measures how quickly the main content becomes visible.

Target: under 2.5 seconds

Interaction to Next Paint (INP)

Measures how responsive the page feels when users interact with it.

Target: under 200 ms

Cumulative Layout Shift (CLS)

Measures unexpected movement of content during loading.

Target: under 0.1

Optimize Images First

Images are usually the largest resources on a GitHub Pages website. Resize them before uploading instead of relying on CSS scaling.

Recommended widths:
  • Hero image: 1600px
  • Banner: 1280px
  • Card image: 640px
  • Thumbnail: 320px

Use WebP whenever possible. A 400 KB JPEG often becomes 120–180 KB as WebP.

Prevent Layout Shift

Always provide width and height attributes for images. 

<img src="hero.webp" width="1600" height="900" alt="Technical SEO dashboard">

This reserves space before the image loads and improves CLS.

Reduce Render-Blocking Resources

Load analytics scripts asynchronously and avoid large external libraries unless they are essential. 

<script async src="https://www.googletagmanager.com/gtag/js?id=G-XXXXXXXXXX"></script>

Keep custom CSS in a single file or a single style block for small projects.

Use System Fonts for Speed

System fonts avoid additional network requests. 

font-family: Inter, system-ui, sans-serif;

If you use a hosted font, limit the number of weights and styles.

Keep the DOM Reasonable

Extremely large pages with many nested elements can slow rendering. The ETKFreelancer homepage is intentionally divided into clear sections rather than one massive block.

Measure Before and After

Use PageSpeed Insights:

https://pagespeed.web.dev/

Test the live GitHub Pages URL, not the local file.

A Practical GitHub Pages Checklist

  • Convert large images to WebP
  • Specify width and height
  • Keep analytics scripts async
  • Avoid unnecessary libraries
  • Use system fonts when possible
  • Compress screenshots and banners
  • Retest with PageSpeed Insights

How This Relates to ETKFreelancer

The ETKFreelancer project uses a lightweight static structure, repository-aware URLs, structured data, internal linking, and asynchronous analytics loading. The next performance gains will mainly come from image optimization and careful control of additional assets.

Conclusion

A fast GitHub Pages website does not require a complex framework. Start with images, prevent layout shifts, reduce blocking resources, and keep the page structure clean. Performance improvements become much easier when crawlability, analytics, and internal linking are already in a healthy state.
